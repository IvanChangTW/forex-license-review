SECTION 01

關鍵術語

承接 v1 的術語（SSOT、codex_tier、baton、scope），本篇新增以下核心概念：

Glossary · Vol. II

native 25.6KB cap
Claude Code 對 MEMORY.md 的載入上限：「前 200 行或前 25,600 bytes、誰先到算誰」，超出尾端靜默不載。中文每字 3 bytes → byte 遠比行數先爆。本篇一切大動作的根源約束。
compiled MEMORY.md
sync 把 MEMORY.shared.md + MEMORY.<profile>.md 兩段索引串接成的開場全載檔；office / home 各自編譯、共用 shared 段。
demote / detail index
把索引行從全載索引剪進 lazy「詳細索引」檔（開場不載、需要時 Read、grep 照常可及）。零程式碼的手動 tiering，檔案本身不動。
fail-closed gate
寫入前的 byte 硬防線：超線就拒寫、保留舊版、exit 1；-Force 才能 override。與偵測端共用同一份 common.env 常數。
tripwire
提早警告線。例：shared 索引 17,800B ＝「再加條目就會把最大 profile 推破軟線」的預警點，設在真撞牆前約 1KB。
orphan（孤兒檔）
建了檔卻沒被任何索引 / detail index / dashboard 收錄——開場與路由都看不到、且無任何信號。全系統唯一「發生時零信號」的失效模式，7/2 起雙側自動偵測。
binding constraint
當下真正先撞到的那條限制。它會遷移：Codex AGENTS 32KB（5月）→ Claude native 25.6KB（6/23 起）→ 兩 profile 中較大的 home（7/2 起）。盯錯約束的優化都是白做。
SECTION 02

SECTION 03

里程碑時間軸

7 週不逐日記，按 10 個 architectural milestone（橘點＝關鍵轉折）：

M1 · 05/16孤兒索引事故：手動 audit SOP 誕生

project_receipt_scanner.md commit + push + sync 全做了，卻忘了編索引——檔案在、索引沒有，新對話 auto-load 看不到，等於不存在。事後寫下含 comm -23 audit 指令的 SOP 檔：「定期跑、抓孤兒」。這是需要人記得跑的 on-demand 指令；它的自動化版本要到 7/2 才落地，而那時這份手動 SOP 早已被併進其他檔——7/2 體檢當天在一個落後 44 天的 memory 目錄裡挖到它的殘影，恰好見證「手動 SOP → 自動 gate」的完整生命週期。

M2 · 05/31→06/16衝突標記潛伏兩週：conflict-marker 掃描進 health

5/31 跨端 merge 漏清的 >>>>>>> 躺在 log.md 兩週才被揪出——git diff --check 只查未 commit 的 diff、抓不到已 commit 進去的孤兒標記。修法：health 加行首標記掃描。誠實註記：當時只進了 .ps1，常做跨端 merge 的 home 端（.sh）反而沒有——這個不對稱要到 7/2 才補齊。

M3 · 06/17git_sync_health：跨對話兜底「半成品遺失」

三檢：① working tree dirty ② 本機 vs origin ahead/behind（fetch 後比 origin、絕不用「本機 HEAD 沒前進」反推對方沒 push——同期一次誤判的直接教訓）③ MEMORY 索引指向的檔是否存在。唯讀、掛在 sync 之後，定位是「唯一能跨對話兜底半成品遺失的機制」。

M4 · 06/22fan-out 深審：「勿拆 topic 檔」裁定

反直覺結論：MEMORY.shared.md 每次開對話全載，拆成 topic 檔在全載模式下不省任何 context、還會因 sync 明文 skip MEMORY.*.md 而讓拆出的條目靜默漏載。裁定寫進索引檔頭 inline 邊界：不拆，逼近門檻先合併/降級。

M5 · 06/23★ 綁定約束遷移：native 25.6KB、byte 先於行數

tiering survey 驗證 native loader 行為後三個結論：行數維度永遠不 binding（實測 81 行 / 上限 200、只用 40%）；byte 維度早就在燒（當時已 90%+）；原本只量行數的守門形同空轉——量錯維度的監控等於沒有監控。約束從「Codex AGENTS 32KB」正式遷移到「Claude native 25.6KB」。Codex 端因有 tier 編譯反而寬裕（72%）；Claude 端攤平全載、成為結構性弱側。

M6 · 06/24profile split：25 條單端條目連檔搬家

順著新約束的第一刀：shared 索引是兩個 profile 共同吃的天花板大宗，把 25 條「其實只有單端需要」的條目連檔搬進 office/ / home/。判準寫進索引檔頭：新增條目先問「另一端開場需不需要」，再決定 scope。

M7 · 06/25SOP 從紀律變 enforcement：hook 強制注入

公司端漏跑一次晨間 SOP 後，開工/收工觸發語改由 UserPromptSubmit hook 自動注入 SOP 清單（跨平台、公司+家裡 Claude 共用）——不再依賴 model attention。v1「從紀律到自動化」哲學在 SOP 層的延伸：紀律寫成文件會被忘，寫成 harness 就不會。

M8 · 06/26propagation-drift 收斂：fail-closed 成為預設

公司 Codex 審出兩個月架構債、Claude CLI 接力修：13 條 profile split 後的斷鏈；sync-codex stop line 從「只警告仍照寫」改成「超線 fail-closed 不寫入」——虛設的線變成真的牆；閾值全數收進 common.env（寫入端＋偵測端、PowerShell＋Bash 四路同源）；新增 pointer-integrity 檢查；cross-scope 豁免範圍正式裁定（只豁免兩份 dashboard 與 log.md）。

M9 · 06/27-28★ 16-agent 架構審：牆已經撞上了

抓到最痛的一條：office 全載 MEMORY.md 已達 26,874B、破 25,600 硬上限——每個新對話正在靜默漏載尾端索引，且無任何告警。修整三層：P0 demote 12 條 office 條目進新生的 lazy detail index（26,874→24,202B）；P1 sync 寫入前加 byte 硬 gate（fail-closed）；P2 health 補 shared 索引 tripwire（17,800）。三層剛好是「修這次、擋下次、預警下下次」。

M10 · 07/02★ 38-agent 全面體檢 + 三刀 + 三端 baton

主迴圈先釘一手事實 → 5 維 fan-out（模型按難度配）→ 每條 finding 對抗式查證 → 綜整。38 agents、31 條 findings 存活、1 條被反駁剔除、4 條 severity 被修正。當天三刀落地：① demote 13 條 + CURRENT_WORK 瘦身（94%→78%、runway x3.7）；② 修 CRITICAL——sync-office 寫死單一目錄、同機另一專案 memory 落後 44 天無告警 → 改掃全部目錄＋收工自動健檢；③ health 補洞包——orphan 偵測雙側（M1 的自動化終點）、conflict 掃描補 .sh（M2 的終點）、三 scope 索引檢查、備份滾動清理。隨後 handoff 派三端接棒，公司 Codex 一小時內完成並回報，零口頭。

本章即「現在的架構長什麼樣」，供任何一端 onboarding。

4.1 三層載入模型

demote 是零程式碼的手動 tiering。7/2 體檢的結論之一：它用一個 commit 抓到自動化 tiering 八成的價值；自動化（claude_tier 軸）掛了明確 trigger（demote 後 shared 再逼近 17,800）才啟動。

SECTION 05

Baton 演化：Stage 6-7

v1 記到 Stage 5（markdown 留存層 primary、口頭 secondary）。這 7 週加了兩階：

Stage 6（06/25）— Harness enforcement

開工/收工 SOP 由 UserPromptSubmit hook 強制注入——baton 的「接棒儀式」不再依賴 agent 記得。紀律寫成文件會被忘，寫成 harness 就不會。

Stage 7（07/02）— 結構化多端派工

handoff 檔按端分段、每條任務帶驗收標準、檔尾留回報欄；路由接進兩份 CURRENT_WORK（Claude 端）與 AGENTS 編譯（Codex 端 detail tier），四端誰先開對話誰看得到。首次實測：公司 Codex 一小時內自主完成、用 fake-tier 探針驗收、回寫 handoff 檔——全程零口頭。

Stage 1 隱含 → 2 命名 → 3 跨組合 → 4 payload 對比 → 5 markdown 主導
       → 6 harness 強制注入（6/25） → 7 結構化多端派工（7/2）
這套架構真正的價值不是儲存，是讓「整理、歸納」變成多端共享的迴路。

驗證員抓到的數字灌水

流程四段：

  1. 主迴圈先釘 ground truth：byte 數、gate 常數、health 一手輸出、目錄狀態——全部親測寫成「已知事實」餵給 agent，讓 fan-out 的角色是「對著事實查證」而非憑記憶臆測。
  2. 5 維 fan-out、模型按難度配：scaling 給最強模型、機械枚舉（frontmatter / 索引 / 連結 / scope 全量驗證）給輕量模型、其餘中間檔——下游反正有對抗式驗證兜底。
  3. 每條 finding 一條獨立驗證 agent、任務是「試著反駁」：不確定標 PLAUSIBLE、佐證不成立標 REFUTED、severity 灌水打回。戰果：一條剔除、runway 增幅 x4 重算為 x3.7、兩條 severity 調降、「已發生」措辭修正為「逼近臨界」。
  4. 綜整後同日落地為 code：體檢報告不是產出物，修完的系統才是——三刀＋完整測試矩陣（雙側正負面探針、gate 實測、端到端 sync 兩輪）當天閉環。
反向護欄（6/30、另一專案的教訓）

fan-out ≠ 更好的解。根因在外部系統、且有廉價手動復原時，多 agent 驗證只會製造進展假象。這條反向護欄與方法論本體同等重要。

SECTION 08

定位：實務上沒有統一最佳解

Agent 長期記憶至今仍是 open problem。主流路線與代價：

路線代表付費點代價
自動萃取派mem0、Zep/Graphiti、各家內建 memory讀取端（自動抽取）精度差、存錯存廢話、內容不歸使用者
向量檢索派RAG over notes建索引＋檢索幾百檔量級下精度輸給 hand-curated index + grep
策展派（本架構）repo-as-truth + 編譯視圖 + 治理寫入端（策展費＝那 40%）換得精度、跨端一致、可稽核、可攜

但不管哪派，最後都收斂到同幾個不變量——這正是「長期記憶＝不斷整理、歸納」的工程對應：

  1. 分層載入（熱/溫/冷）——與人腦工作記憶/長期記憶同構
  2. 歸納（consolidation）是一等公民——daily log → monthly review → 升格；demote 是同一件事的反向
  3. 遺忘是功能不是 bug——lifecycle、archive、prune；25.6KB cap 逼系統面對取捨，反而是健康的約束
  4. 治理迴路決定壽命——沒有 health/gate 的記憶系統必然腐化，差別只是三個月還是一年
沒有統一最佳解，但有「給定約束下的唯一合理解」——2 機 × 2 agent × 金融合規 × 跨日續工，幾乎唯一指向策展派。

SECTION 10

設計哲學：7 條全數存活 ＋ 新增 4 條

v1 的七條（explicit authoring / git SSOT / local-first / markdown 可攜 / filesystem 統一層 / 方法論寫進 memory 自己 / 最小爆炸半徑）經 7 週實戰無一被推翻。新增：

8 · Fail-closed by default

gate 寧可擋下同步也不寫出會靜默漏載的檔；讀不到設定就用保守內建值。虛設的警告線一律升級成真的牆。

9 · Detect → remediate 必須閉環

只偵測不修復的檢查會退化成背景噪音（lifecycle WARN 連喊 49 天無人動是活教材）；每條新檢查都要想好「喊了之後誰動、怎麼動」。

10 · 不做的事要掛可觀察 trigger

「暫不做」不是「不做」，是「條件 X 成立時重評」；tier 自動化、skill layer、向量檢索都掛著明確條件。

11 · 點名綁定約束、追蹤它的遷移

約束會動（32KB → 25.6KB → binding profile 是 home 不是 office）；盯錯約束的優化都是白做。

SECTION 12

結論

v1 的結論是「9 天、每天一步、compound effect 真實存在」。這 7 週的結論是它的下一章：

1 · 約束遷移比功能增長更能定義架構的階段

5 月的系統圍繞「把四端接起來」生長；6-7 月的系統圍繞「25,600 bytes」重組。找到真正 binding 的那條線，之後每個決策都有了排序依據。

2 · 治理的成熟度是一條四段梯

從「人記得」到「系統喊」到「喊了有人修」到「修完變成新的 gate」。孤兒索引從手動 comm 指令（5/16）走到雙側自動偵測（7/2）；同一條演化在衝突標記、byte 守門、SOP 注入上各自重演。這條四段梯是可遷移的 pattern。

3 · 多 agent 的價值在對抗式驗證，不在人多

38 個 agent 裡最有價值的是那些「試著反駁」的：剔除一條假 finding、把 x4 打回 x3.7、把「已發生」修正為「逼近臨界」。fan-out 產生覆蓋，驗證產生真實——而 6/30 的反例提醒：兩者都不能替代「根因在不在你手上」的判斷。
